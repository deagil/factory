# 0045. Object endpoints and workflows

- **Status:** Accepted
- **Date:** 2026-11-09
- **Supersedes:** [0001](0001-one-action-registry.md), [0010](0010-workflows-only-listeners.md), [0011](0011-who-actions-run-as.md), [0022](0022-generated-actions.md), [0024](0024-roles-and-permissions.md), [0027](0027-http-api-shape.md) and [0028](0028-mcp-tools.md) where they say otherwise.
- **Amends:** [0042](0042-approval-rules.md) and [0043](0043-approval-limits.md): approval rules cover config drafts only.

## Context

Phase 1 made every capability an action or a query, each on its own route (`POST /actions/deal.moveStage`) and MCP tool, and decision 0011 had workflows act as themselves with permissions derived from the actions their steps run. A design review on 9 Nov 2026 found three problems with that:

- **Actions are too small to be endpoints.** Business processes are several changes with checks between them ("this account is mine", "within limits", "still pending"). As actions, the checks live in handler code nobody can see, and callers string actions together themselves, outside any transaction.
- **Derived permissions don't hold up.** A workflow that refunds a payment needs refund permission, so only a finance person can publish it, but the reason to have the workflow is that support can start it. And a role that grants an action grants it everywhere, so there was no way to say "payments are made only through `payment_make`".
- **Two ways to change a record.** Generated `update` and hand-written actions that own a field (`deal.moveStage` owns `stage`) both write records, with `readOnly` lists to keep them apart.

## Decision

**Principles.** A few building blocks used the same way everywhere, one way to do each thing, each capability defined once and the same on every surface. Plain words over jargon.

### Endpoints

The only endpoints are **object endpoints** and **workflow endpoints**. A caller's role is checked once, at the endpoint.

- **Object endpoints** are generated by `defineObject` for every object, with no opt-in. Each runs the object's generated action of the same name as a one-step run.

  | Endpoint | Does | MCP tool |
  | --- | --- | --- |
  | `GET /<objects>` | List, with query parameters to filter, sort and page (a cursor) | `<object>_list` |
  | `GET /<objects>/{id}` | Read one record | `<object>_get` |
  | `POST /<objects>` | Create | `<object>_create` |
  | `PATCH /<objects>/{id}` | Update the fields given; `If-Match` carries the version | `<object>_update` |
  | `POST /<objects>/{id}/archive`, `/restore` | Hide a record from lists, or bring it back | `<object>_archive`, `<object>_restore` |
  | `GET /<objects>/{id}/history` | The record's field history and the runs that touched it | `<object>_history` |

  There is no `PUT`: one way to update. Owned fields (`actions.update.readOnly`) go; role rules decide who writes a field.

- **Workflow endpoints:** a published workflow that starts when called is `POST /workflows/<name>`, with its declared input, output and errors. A workflow marked `read_only: true` is `GET /workflows/<name>` with query parameters, and validation proves it never writes. Runs are resources: `GET /runs/{id}`.
- **Every surface comes from one registry:** HTTP and OpenAPI, MCP (one tool per endpoint, named exactly as the endpoint), `system_describe`, the web app's screens, forms and workflow buttons, and later the CLI. Agents build workflows through the same endpoints the web app uses. **Actions are never on a surface.**

### Actions

An action is reusable typed code that a step runs: `defineAction` with Zod input and output, declared error codes and its own unit tests. It fully happens or it doesn't. Each action is one of two kinds:

- **Internal:** touches only our own database, so a rollback undoes it. The generated record actions (`deal_get`, `deal_list`, `deal_create`, `deal_update`, `deal_archive`, `deal_restore`), ready-made checks ("record belongs to caller", "within a limit", "record is in the expected state"), calculations and reshaping. It gets the segment's repository and never opens its own transaction.
- **External:** reaches another system, which a rollback can't undo (`http_send`, `comms_send`, later a payment provider). It runs outside the transaction, with a retry key and retries.

Modules and systems add their own actions. Actions never write logs; the engine records what each step hands back (decision [0046](0046-runs-segments-and-errors.md)).

### Workflows and steps

- A **workflow** is where a business process lives. Client processes are YAML under `config/workflows/`; the core and modules write theirs in TypeScript with `defineWorkflow`, in the same shape, run by the same engine, served on the same endpoints and traced the same way. The draft, approval, actor, API key and invite operations become code workflows, and `system_describe`, record history, config validation and the log reads become read-only code workflows.
- A workflow **starts** when called, when an event happens, or on a schedule (`starts_when`).
- **`input`** defines what it takes, with the same field types as objects. The endpoint checks it before any step runs, and it is also the web form, the MCP tool's schema and the OpenAPI request. **`output`** says what the caller gets back. **`errors`** declares its own error codes, each with a plain-English message, which OpenAPI and MCP list.
- A **step** runs an action, or is built-in control flow that the engine provides and nobody writes: `if` (condition, `then` and `else`), `wait`, `wait_for_approval`, `run` (another workflow), `emit`, `fail` and `output`. The two waits are the **pauses**. There is no `defineStep`.
- Values are `from` a path (`input.…`, `event.…`, `steps.<id>.output.…`) or a fixed `value`. Conditions are field, operator, value: no expression language.
- **Checks are steps.** Any check route code would make is a step that fails with a declared error code.
- **Nested:** a `run` step waits for the child's result; if the child fails, the step fails.

### Running under the service key

Inside a workflow, actions run with full internal access, as a code API runs with its database rights. Getting each step right is the workflow's job, and publishing (below) is the control. The run records the workflow as the actor and the caller as `origin_user_id`; decision 0011's `actor_id` and `origin_user_id` on every row stay, and there is still no `acting_for` or `triggered_by`. `http_send` destinations stay fixed in the workflow file, never taken from data.

### Roles

One set of rules, the same on every surface; routes never carry rules of their own.

- **Endpoints:** which object endpoints and workflows a role may call. A workflow is granted by name.
- **Fields:** which fields a role may read and which it may write, per object. Lists and reads leave out unreadable fields; a write to an unwritable field is refused with a validation error naming the field.
- **Rows:** `own` or `all`, applied to lists, reads and writes. `own` means the record's owner field (declared on the object, for example `owner: "owner"`) is the caller, or for an agent, the person it acts for.
- **Privilege ceiling:** nobody grants, mints or revokes a role or key with authority they don't hold themselves.

Agents still act for a person, never wider than that person (decision 0025).

### Events

Object endpoints and the generated record actions emit `<object>_created`, `<object>_updated` (with the changed fields, before and after), `<object>_archived` and `<object>_restored` in the segment's transaction. A workflow declares its own events with payload schemas and emits them with an `emit` step. Event triggers test the payload, including changed fields and a choice field's column such as `stage.category`. **Workflows are the only listeners;** one dispatcher starts one run per event and matching workflow, exactly once, with a depth limit on chains.

### Approvals

- **Data needs sign-off only through a workflow.** If a write needs approval, roles don't get that write, and a workflow does it with a `wait_for_approval` step, which takes decision 0043's options: approver role, number of approvals, requester and exempt roles, and conditions.
- **Approval rules in `config/approvals/` cover config drafts only.**
- **Two people** for any draft that touches `workflows/`, `roles/` or `approvals/`: the author and at least one different person with the approver role, with no admin exemption.
- One approvals table and one inbox for both. A request is a run waiting at a step, or a draft. A run waiting for approval is a pending resource, so `approval_required` is no longer an error.
- Developer-written workflows reach `main` through `fx ship` and a PR; CI runs their example cases and the PR review is the second person.

### The publish gate

A new or changed workflow starts as a draft and publishes only after:

1. **Validation on save:** step inputs and outputs line up; the actions, fields, choice options and events it names exist; branches cover every outcome; `on_failure` steps exist where they must; `http_send` URLs are fixed in the file; a warning when a workflow takes a record id with no ownership check.
2. **Example cases** in the workflow's own `cases`: a caller, an input or event, fixture records, recorded fakes for external steps, and the expected output or error, writes and emits. One failing case per declared error code, and a wrong-caller case when the input takes a record, are required. CI runs them against a database built from migrations; a running instance runs them in a transaction that is always rolled back, with waits skipped and approvals and external steps faked.
3. **Regression:** every workflow's cases rerun in CI whenever a workflow, action, object or the core changes.
4. **Two-person approval,** as above.

## Consequences

- "What can this role do?" is read from one role file; "what does this process do?" from one workflow file. Neither hides in handler code.
- Moving a deal's stage is a plain `PATCH` until the business needs checks; then roles lose write on `stage` and a `deal_move_stage` workflow does it. Payments are made only through `payment_make` because no role can `POST /payments`.
- Staff can start automation that does more than they can do directly, but only automation that passed the publish gate and a second person.
- The pipeline's stages (identify, validate, retry check, authorise, run, record, commit) move to the endpoint. Retry keys, dry runs (the base for example cases), choice fields, config drafts over git, the loader, Better Auth, the error shape and stateless MCP carry over.
- The move is gradual: `/actions` and `/queries` stay until P2.26, and today's dotted names stay until the tasks that rename them.
- Open, not settled here: team scopes and rules on related records, a protected owner role, API key policy, and the admin approver exemption outside workflows, roles and approvals.
